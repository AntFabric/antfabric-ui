# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AntFabric UI is one component library for AntFabric's web (TanStack Start), desktop (Tauri) and mobile (Expo) apps, written as real components: `@antfabric/ui-react` serves web and desktop, `@antfabric/ui-react-native` serves the phone. Both take the same props. An Astro catalogue (`apps/catalogue`) draws the components themselves, live, on each platform's tab (the phone kit through React Native Web), and shows each one's flows. Neither app consumes the kits yet. The packages are published to npm (`RELEASING.md`). The other root guides: `AUTHORING.md` (how a component is written), `CONSUMING.md` (how an app installs and themes the kits) and `MIGRATION.md` (0.1 to 1.0, every rename).

## Commands

Node 26 (`.nvmrc`), pnpm pinned through `packageManager` in `package.json`. Run from the repository root:

```bash
pnpm install
pnpm dev                          # catalogue on http://localhost:4321
pnpm check [id…|screens]          # the test suite: run after every change
pnpm check literals               # only the literal ratchet
pnpm check parity                 # only parity: draws everything, then compares the snapshot file and tokens.json with reports/parity.json's commit
pnpm check code                   # kit props against the docs, the API conventions, and the packages' import rules
pnpm check conventions            # only the API conventions (reports/api/conventions.md) and their ratchet
pnpm literals:tighten             # lower literals.allow.json to the current counts (never raises one)
pnpm typecheck                    # tsc over core, docs, both kits and the catalogue
pnpm describe [id|tokens [group]] [--json]  # one component's props, parts, recipe, examples, flows and files (or a token group) in one read
pnpm frames <id> [platform] [os]  # where each flow frame's `press` lands
pnpm rerender [id…]               # only the re-render pass of `check`
pnpm report [--json]              # token reads, literals and branches per component (design-system baseline)
pnpm tokens:build                 # rewrite packages/core/tokens.json (W3C Design Tokens file); `check` fails when it is stale
pnpm build                        # check, then static build to apps/catalogue/dist
pnpm build:packages [core|react|react-native]  # the three publishable packages to packages/*/dist (esbuild + tsc)
pnpm verify:packages              # build, pnpm pack, install the tarballs in a scratch project, render and type-check
pnpm preview
```

`pnpm check` with no argument runs everything. Its arguments narrow it to sections and component ids, combined freely: a component id (`button`) renders that component only; the section names are `tokens`, `primitives`, `palette`, `chart`, `agent`, `architecture`, `literals`, `helpers`, `themes` (alias `brand`), `code`, `conventions`, `generic`, `strings`, `defaults`, `recipes`, `docs`, `screens` and `parity`. Flags: `--update-snapshot`, `--no-rerender` (keeps the `@mounted` keys as saved), `--quiet` (no warnings), `--timing`. The typecheck always runs first, so a narrowed check is still not instant. Start with `pnpm describe <id>` before reading a component's files.

There is no linter and no unit-test framework. `pnpm check` is the test suite (about a minute):

- **typecheck** of every package and the catalogue (screens are checked against React Native's own types).
- **docs**: every prop an example, edge case or flow frame passes is declared; icons, tokens and component ids exist; flows line up.
- **code**: each kit's `XProps` has exactly the documented props for its platforms; every `useControllable(value, onEvent)` is declared as `onEvent.changes`; no handler is passed straight through (`onClick={onPress}`).
- **renders**: every example, variant, state, edge case, flow frame and screen, server-rendered on every OS (mac 26/15, windows, linux, browser, ios 26/18, android), failing on any React or React Native Web warning.
- **snapshot** (`reports/renders.snapshot.json`): one hash of every render per component × platform and per screen (`button/web`), taken over resolved values (each `var(--af-…)` replaced by its value for that render's platform and theme, so a token's value changing shows and its name changing does not) and over each element's declarations, not how they were written (the order of a style, `border` against its longhands, React Native Web classes against inline style are the same, so moving a style table into another file is provable); a changed hash fails and lists its keys, so "no pixel changes" is provable. Every render is drawn in two themes, `antfabric` first (the keys above, held by parity) and then `neutral`, a second pass over the same set whose keys end in `#neutral` (`button/web#neutral`, `screen/inbox#neutral`, `button/web@mounted#neutral`). A third pass, `<id>/<platform>#bare` (`button/web#bare`, no screens), is what a product gets before it has said anything: the rest render of each component on every OS, drawn with the kit's own defaults only (the `required` props take their docs `sample`, since a product must pass them), no `ANTFABRIC_STRINGS` (the English strings) and the `neutral` theme, so the kit defaults, the built-in English and empty lists are hashed too. A theme's `data-af-theme-id` and its `<style>` sheet are left out of the hash, since the values they declare are in it. Accept a meant change with `pnpm check [id…] --update-snapshot` and commit the file. A data component also has `<id>/<platform>@mounted` keys: the chart libraries draw their geometry in effects, so the server render of a chart is only its frame, and these hash the markup after it was mounted in the re-render pass (below), through every state, variant, example and edge case, with numbers rounded to three decimals (`roundCoords`: a curve's trig differs in its last digit between Apple Silicon and the Intel CI runner), the same resolved values, folded ids (`scripts/ids.ts`) and declarations (`scripts/snapshot-hash.ts`, shared with the server renders), under reduced motion so a chart is drawn complete. They are compared and accepted like any other key; `--no-rerender` leaves them as saved.
- **parity** (`reports/parity.json`: the commit the library's look is held to, the theme that look now is (`antfabric`) and `accepted`): every snapshot key `reports/renders.snapshot.json` had at that commit (`@mounted` keys and screens included) is still there with the same hash and render count, unless its component or screen id is in `accepted` (`{ "brand": "one-line reason" }`); keys added since are free. No token leaf in `packages/core/tokens.json` that the commit had changes its `$value` or modes (new leaves are fine). Components and files may change freely: parity holds what is drawn, not how. `--update-snapshot` does not rewrite a parity key whose id is not accepted, and names `reports/parity.json` as the file to edit; a meant change is accepted there with its reason, then the snapshot is updated and both files committed. The comparisons need the commit in git history and are skipped with a warning without it.
- **conventions** (`pnpm check conventions`, also part of `code`): `reports/api/conventions.md`, as far as a machine can read it, for every component: no component declares `onChange` (docs or either kit), none declares `collapsed` (disclosure is `expanded`), a `required` prop has no documented `default` (its catalogue value is its `sample`), and every event declared `changes: "<prop>"` is named `on<Prop>Change`. What breaks a rule today is in `conventionsTodo` in `reports/generic.json` (`{ "<id>": ["<rule>: <detail>", …] }`, rules `no-onChange`, `no-collapsed`, `required-no-default`, `change-event-name`): a violation not listed fails, and a listed one that now passes must come off, so the list only shrinks.
- **styles probe** (`pnpm check generic`): beside `styles` winning over the kit's inline styles, a component whose recipe has a `root` part must draw a root of its own in every drawing, never only its other parts around a nested component's root (QuestionPanel's collapsed bar, a phone sheet with no `root`). What fails today is in `stylesProofTodo` as `<kit>:root`.
- **code** also holds the import rules: `recharts` only under `packages/react/src/data/` and `packages/react/src/components/data/`, `react-native-gifted-charts` and `gifted-charts-core` only under the same two folders of `packages/react-native/src/`, `@tanstack/table-core` only under `packages/core/src/table/` (a rule for a dependency the kit does not have: the Table's layout, sort and formats are the kit's own, `packages/core/src/chart/grid.ts`), nothing third-party under `packages/core/src/chart/`, and a file under `src/templates/` imports only its kit's public entries.
- **re-renders** (`scripts/rerender.tsx`, happy-dom): each component mounted once and updated through its states, variants, examples and flow frames, with every control hovered, pressed and focused, failing on warnings that only appear on update (a `border` shorthand fighting `borderColor`). It also writes the `@mounted` hashes that `check` reads.
- **focus and keys** (in the re-render pass, web and desktop, in a root of its own): every control a keyboard reaches must draw something when focused for real; the arrow keys must move in every menu, menubar, toolbar, tablist, radiogroup and listbox; a modal must take focus when it opens and keep Tab inside. What fails today is `focusTodo` and `keysTodo` in `reports/generic.json` (`"<id>/<platform>: <what>"`); a failure not listed fails, a listed one that passes must come off, and `AF_TODO_WRITE=1 pnpm rerender` records them (only when a check is added).

The scripts run under `tsx` with `apps/catalogue/scripts/native.mjs`, which resolves `react-native` to react-native-web in Node. `pnpm-workspace.yaml` lists the packages allowed to run install scripts (`allowBuilds`).

## Architecture

- **`packages/core`**: what both kits share. `tokens.ts` (`shared`, `themes.*` colour and shadow, `profiles.*` per-platform size and type: that is how a control is 34px on desktop and 44pt on mobile), `tokensCss()` and `kitCss` (the variables under `[data-af-platform]` / `[data-af-theme]`, plus keyframes), `resolveTokens()` for React Native, `formatShortcut`, `MOTION`.
- **`packages/react`** (`@antfabric/ui-react`): `src/components/<category>/<id>.tsx`, one file for web and desktop. Inline styles over `t` (every token as `var(--af-…)`). `usePlatform()` gives platform, OS, version and Liquid Glass; `useInteraction()` gives hover/press/focus as state; `lib/style.ts` has the layout helpers (and `mirror` / `rtl` for right-to-left); `lib/focus.ts` (`useOverlayFocus`, `useFocusHandoff`), `lib/roving.ts` (`useRovingKeys`), `lib/announce.ts` (`announce`) and `lib/root-props.ts` (`RootProps`) are the keyboard, screen-reader and pass-through contracts every component keeps (AUTHORING.md). `AntFabricRoot` carries the attributes and the stylesheet, and takes `locale`, `dir` and `autoFocus`.
- **`packages/react-native`** (`@antfabric/ui-react-native`): the phone. `createStyles((t) => …)` over `useTheme()` tokens, `font(weight)` (fonts by file) and `fontScale` (Dynamic Type), `usePress()`, `Enter` / `useEnter` and `useReducedMotion` (React Native Animated, no Reanimated), `GlassSurface` (expo-glass-effect when the app has it), `lib/a11y.ts` (`announce`, `hitSlopTo`, `useBackHandler`) and `lib/root-props.ts`.
- **`packages/docs`**: what the catalogue says about each component, as typed TypeScript: `components/<category>/<id>.ts` (props as documented, platforms, examples, edge cases, a11y, flows), `screens.ts` (screen metadata), `platforms/*.ts` (the feature matrix and the notification design). `components/index.ts` lists every file explicitly so plain Node scripts can load it.
- **`apps/catalogue`** is a static Astro site whose previews are React islands (`client:only`):
  - `src/preview/kit.tsx`: `Stage` (each kit's providers), `Thing` (a component with its documented defaults), `SceneNode` (draws the docs' scenes with either kit).
  - `src/islands/`: `Playground` (controls, event log, usage), `Flows` (the swimlane flowchart and its live stage), `Gallery` (examples, variants, states, edge cases), `Preview`, `Tile`, `Trio`, `ScreenView`.
  - `src/lib/prefs.ts`: the visitor's platform, OS, version and scheme (light or dark), shared by `lib/runtime.ts` (the page's switches) and every island.
  - Search (the box in the top bar, ⌘K or /): `src/pages/search.json.ts` builds the index from the docs and from the `PAGES` sources' h2s; `lib/search.ts` ranks it; `lib/search-box.ts` draws the results and gives each page's h2 an id, so `/foundations#colour` lands on its heading.
  - `src/screens/<id>.tsx`: whole screens, composed from one kit; not shipped by any kit.
  - `astro.config.mjs` aliases `react-native` to react-native-web, lucide's native icons to its DOM ones, and stubs `expo-glass-effect`.
- **Dev server:** packages export TypeScript source directly; there is no package build step.

## Writing components

`AUTHORING.md` at the root is the authoritative guide. Rules that are easy to break:

- **Two files, one API:** `packages/react/…/<id>.tsx` and `packages/react-native/…/<id>.tsx`, exported from the category `index.ts`, with the docs in `packages/docs/…/<id>.ts`. Props are exactly the documented ones for that kit's platforms.
- **Tokens:** read `t`; never hard-code a colour or a size that has a token. Sizes differ per platform through the tokens, not through code. Paths are the product's Tier 2 names, nested the way its generated object nests them: the first word is the group and the rest one camelCase key (`t.fg.onBrand`, `t.control.hMd`, `t.text.bodySm`), and a variable is `--af-` plus the kebab-cased path (`cssVarName`: `--af-fg-on-brand`). `reports/baseline.json` is the first scan's record and keeps the old names.
- **Generic, not AntFabric:** no product content in kit code (no fixed menus, product names, "Fabric", recorder, desktop-app actions); a product passes it through props and slots. Every recipe-backed component takes `styles?: PartStyles<"<id>">` (both kits, passed to `useRecipe`, every part applying its whole `r.<part>`; `reports/generic.json` `stylesTodo` lists the ones not converted yet, and `pnpm check code` holds the list), and fixed text reads `useStrings("<id>", strings)` from `packages/core/src/strings/<category>.ts` with English defaults equal to the old text (`s.parts` where the React text was several children; the literal ratchet's `text` count only goes down). `styles` and `strings` are universal props: the docs do not list them, nor the pass-through props every component takes through `RootProps` (`id`, `className`, `data-*`, `aria-*`, `ref`; on the phone `testID` as a prefix for its parts, `nativeID`, the accessibility label and hint).
  - **Precedence for one part, last wins:** the recipe, the theme's recipe override, the kit's own inline styles for the part (prop- and state-driven), `styles[part]`, then `style` on the root. `styles` is the per-part escape hatch, so it beats anything the kit computes for the part. `r.<part>` is the recipe, the theme and `styles[part]`; a part the kit also styles inline is drawn with `partStyle(r, part, …inline)` (`lib/recipe`, both kits), never `css(r.root, inline)`. `pnpm check generic` probes every converted component's parts (`stylesProofTodo` in `reports/generic.json` lists the ones that fail, with their parts).
  - **Strings, read from the syntax tree** (`pnpm check strings`): every key is read by every kit that draws the component, unless it is declared platform-only next to the keys (`export const displayOnly = { card: { select: ["mobile"] } } as const satisfies OnlyOn<typeof display>`; the named kit reads it, the other must not); a call whose result is thrown away (`void s("select")`) is an error; the variables are the template's placeholders (and `count` for a plural); an unknown key is an error. `stringsTodo` lists the components that break one.
  - **Docs defaults equal kit defaults** (`pnpm check defaults`): a component drawn with all its documented defaults draws the same markup with any one left out; `defaultsTodo` (`<id>.<prop>`) lists the ones that do not. Each of the three lists only shrinks: take an entry off in the commit that fixes it (the check fails if you do not).
- **Events:** call them with their documented args only (`onClick={() => onPress?.()}`). A prop a press changes goes through `useControllable`, and its event is declared with `changes`.
- **React kit:** states come from `useInteraction`, never CSS `:hover`; borders are longhands (`borderWidth`, `borderStyle`, `borderColor`).
- **React Native kit:** every `Text` sets its own colour, size and `font()`; every `Icon` gets a `color`; never `{str && <X />}` with a string or number.
- **Flows:** steps (`data`, `trigger`, `event`, `state`, `effect`, `motion`, `result`) are drawn as a swimlane flowchart; a trigger that arrives from the server or the OS sets `lane: "system"`.
- **Data components** (category `data`; docs `group`: `kpi`, `chart`, `panel`, `table`) ship from each kit's `./data` subpath (`@antfabric/ui-react/data`, `@antfabric/ui-react-native/data`), never the root entry, so an app that never imports it carries no recharts or gifted-charts (`pnpm verify:packages` bundles a root-only consumer to prove it). Components are `components/data/<id>.tsx`; what they share (`ChartFrame`, `ChartTooltip`, `Legend`, `rechartsTheme()` / `giftedTheme()`, resolved chart tokens) is `src/data/`. The libraries take plain colours, never `var(--af-…)`: the React kit resolves its tokens with the theme `usePlatform()` carries, the phone reads `useTheme().t`. They read `chart.*` and `data.*`, never `brand.*`, `success.*`, `danger.*` or `warning.*`. recharts and gifted-charts draw only once mounted, so the server render of a chart is its frame; the mounted markup is checked in `pnpm rerender`, and `apps/catalogue/scripts/ids.ts` folds the ids they number before anything is hashed. The catalogue lists them in a Data section after the three levels (`byDataGroup()` in `lib/library.ts`).
- **Shell components** (the app frame and the pictures of native surfaces) ship from each kit's `./shell` subpath (`@antfabric/ui-react/shell`, `@antfabric/ui-react-native/shell`; `src/shell/index.ts`), never the root entry. Their files stay in `components/shell/` and `components/notifications/`; a component moves by its line joining the shell entry and leaving the root's or its category's `index.ts`. `pnpm check code` fails when a kit file outside `src/shell/` imports the shell entry or a file it re-exports, `kitComponent` in `preview/kit.tsx` looks there too, and `pnpm verify:packages` bundles everything the roots export to prove none of it is reached.
- **Chat components** (the conversation idiom) ship from each kit's `./chat` subpath (`@antfabric/ui-react/chat`, `@antfabric/ui-react-native/chat`; `src/chat/index.ts`), never the root entry, which stays the generic set a product composes its own screens from. It holds Message, Composer, ReactionPill, ThreadSummary, TypingIndicator and MessageDivider, and MessageActions on the web (the files stay in `components/messaging/`); AttachmentCard, SwipeRow, Fab and the agent components stay in the root. As with `./shell`, `pnpm check code` fails when a kit file outside `src/chat/` imports the chat entry or a file it re-exports, and neither the root, `./data` nor `./shell` reaches it. So the kit has four entries: the root, `./data`, `./shell` and `./chat`.
- **API conventions** (`reports/api/conventions.md`, the 1.0 rule book; every rename is in the ledger under `reports/migration/`). Four headline rules: a prop a component can change is reported by `on<Prop>Change(next)` (declared `changes: "<prop>"`, through `useControllable`; there is no `onChange`); an item in a list is named by `key: string`, and a prop that names an item holds a key; a panel, section, rail or bar that opens and closes takes `expanded` / `onExpandedChange`, positive, never `collapsed` (`open` is only for overlays); an axis chart reads its category from `x` and its value from `y`, a part-of-whole chart reads `name` and `value`, and `label` is only ever the accessible name. Also: a `required` prop has no docs `default`, its catalogue value is its `sample`. `pnpm check conventions` holds the checkable ones.
- **Item shapes** (`packages/core/src/items.ts`): `MenuItem`, `NavItem`, `ActionItem` and `AppMark`, re-exported as types from each kit's root. A component that needs more extends one in its own file; nothing adds fields to them. Items carry no functions. A menu row is matched by `key ?? label` (`menuItemKey`).
- **AntFabric's content in the docs, not the kits:** a prop's `default` is the kit's (generic) default and its `sample` is what the catalogue draws (`withDefaults` uses `sample ?? default`; `components.json`, `llms.txt` and `pnpm describe` print both). A matrix row may be `{ prop, cases: { name, props }[] }`, drawn in place of the plain row's values. AntFabric's copy is `antfabricStrings`, shipped from the opt-in entry `@antfabric/ui-core/antfabric` (`packages/core/src/antfabric.ts`; never core's root, so a generic product does not bundle it) and re-exported as `ANTFABRIC_STRINGS` by `@antfabric/ui-docs/samples`, which also holds the sample data (one file per chrome category); `Stage` passes it as `strings` to both roots in both theme passes. An AntFabric app keeps 0.1's look and wording with `theme={themes.antfabric} strings={antfabricStrings}`. `defineTheme` without `extends` starts from `themes.neutral`; `extends: null` is the raw schema (presets only).
- **Sample data and copy:** sample data is AntFabric's own (channels like `#platform-eng`, real names, AI agents named "Fabric"), never lorem ipsum. Copy is plain and specific.
- **Owner decisions:** calls that need the owner's decision go in a GitHub issue, stating what the components do now and naming the component.

## Design system

The tokens move from a flat file to tiers, component tokens and per-part recipes both kits read.

- **`pnpm report`** (the scan is `apps/catalogue/src/lib/scan.ts`, `--json` for everything): token references, colour and dimension literals and platform branches per component file, plus tokens without a description, unread, equal in light and dark. `reports/baseline.json` is the first scan; later numbers go down against it.
- **The literal ratchet.** A colour literal (hex, `rgb(`) or a non-zero number on a size key (`padding: 7`) in a component file is an error beyond the file's allowance in `packages/<kit>/literals.allow.json` (`{ colours, dimensions }`; a file not listed may hold none). `pnpm check literals` runs it alone and names the file, the counts and the lines. Counts only go down: when you remove literals, run `pnpm literals:tighten` in the same commit (it refuses, listing the files, if any count went up). Unitless ratios (`lineHeight: 1.2`, `opacity: 0.5`, `scale: 0.97`) are reported by the scan, not banned; what counts is at the top of `scan.ts`.
- **No new literals.** A size or colour in a component reads a token: a semantic one when its role fits (`space.*`, `radius.*`, `control.*`, `text.*`), otherwise a component token named in the product's style (`chip.removeSize`, `osNotification.macRadius`). Drawing geometry lives in `packages/core/src/art.ts`. Only a demo stage size or a 1px optical nudge may stay, marked `/* structural: why */` on its line, which `pnpm report` lists as annotated. React negatives use `neg(t.space.xs)`; the snapshot folds px-only `calc()`.
- **`packages/core/tokens.map.json`**: where each token leaf was copied from (a product Tier 2 name such as `--fg-body`, `mobile:<path>`, `proposal` or `unmapped`). `pnpm check` fails when a leaf has no entry or an entry names no leaf. `tokens-map.mts --drift` (with `ANTFABRIC_REPO` and `ANTFABRIC_MOBILE_REPO` set to the product checkouts) writes `reports/drift.md`, gitignored, with the values that have moved in the product since the copy.
- **`/architecture`** in the catalogue draws the system from the same scan on every build: the five words, packages, token flow, a per-component inspector (`/inspector.json`), the kit matrix and the findings (`src/lib/findings.ts`, each `file:line` checked by `pnpm check architecture`). Extend this page instead of writing new docs.
- **`packages/core/tokens.json`**: the tokens as a W3C Design Tokens (Format Module 2025.10) file, generated by `pnpm tokens:build` from `tokens.ts`, `descriptions.ts` and the map (`src/dtcg.ts`, import `@antfabric/ui-core/dtcg`), committed and checked by `pnpm check tokens`, served at `/tokens.json`. `$value` is light/desktop; other modes are under `$extensions["com.antfabric"].modes`.
- **`packages/core/src/primitives.ts`** mirrors the product's Tier 1 (`pnpm primitives` writes it from the product checkout named by `ANTFABRIC_REPO`; `pnpm primitives --check`, or `pnpm primitives:check`, exits 1 when the product has moved and 0 when there is no checkout, as in CI). `tokenSource` in `tokens.ts` holds a leaf as `"{primitives.color.neutral.900}"` when it is one, a literal when it has drifted or has no product token; `tokens` is the same tree resolved (what the kits read), `tokensCss()` emits `--af-p-…` once and `--af-fg-body:var(--af-p-…)`, and no component reads a primitive (`pnpm check` fails if one does).
- **Themes.** `defineTheme({ name, extends, brand, fonts, tokens, recipes })` (`packages/core/src/theme.ts`) is an override set over `tokens.ts`; `antfabric` is the empty theme (id `""`), so it draws exactly what the parity commit drew, and `neutral` (a shadcn-like preset) is what both kits draw when no theme is given (the context defaults in `platform.tsx` and `theme.tsx`, and the outermost `AntFabricRoot` / `ThemeProvider`; a nested one inherits its parent's). Everything `pnpm check` and `pnpm rerender` draw for the original keys passes `theme: antfabric` explicitly. It is drawn one layer at a time (shared, scheme, profile, OS; base then theme at each) by `tokenValues`, `resolveTokens(…, { theme })` and `themeCss(theme)`, which is scoped by `[data-af-theme-id]`, never `:root`. `pnpm check themes` holds all three equal.
- **Scheme, theme, root.** `scheme` is light or dark; `theme` is what a product restyles (a theme object, never a string: both roots throw on one). Only a theme `defineTheme` built reaches a sheet or the phone (a registered-symbol mark; a theme stored as JSON goes back through `defineTheme`), and its values may not carry `;{}<>`, backslashes, comment markers or unbalanced quotes and brackets. `AntFabricRoot css`: `true` ships the base sheet and the theme's, `"theme"` only the theme's (a host that loads the base once, as the catalogue does), `false` neither (the host adds `tokensCss() + kitCss` and `themeCss(theme)`); a host with no root writes `rootAttrs({ platform, os, scheme, theme })` itself and passes `theme` to `AntFabricProvider`.
- **Tenant branding.** A brand is part of a theme: `defineTheme({ name, extends, brand })`, passed as `AntFabricRoot theme` (web) or `ThemeProvider theme` (phone). `ThemeInput.brand` takes `Partial<BrandTokens>` (`packages/core/src/brand.ts`: `primary`, `accent`, optional per-theme `soft`, `softHover`, `onSoft`, `tint`, and `fonts: { sans, display }`), expanded per scheme by `brandValues` into the theme's sets; `resolveTokens(profile, scheme, { os, theme })` is memoised by theme id and frozen. A brand moves only `BRAND_PATHS` and `BRAND_FONT_PATHS` (the phone's `font.file*` only on the mobile profile; `fg.onBrand` follows the primary); `pnpm check themes` (still `pnpm check brand`) holds it there. `@antfabric/ui-core` ships Geist and Figtree (`fonts.css`, `fonts/Geist-*`, `fonts/Figtree-*`); Satoshi is not in the repository (its licence forbids passing it on) and `verify:packages` fails if it reaches a tarball. Never hard-code a tenant: pass the theme in.
- The product repo's checkouts (`ANTFABRIC_REPO`, `ANTFABRIC_MOBILE_REPO`) are read, never edited, and nothing from them is committed here.

## CI and releases

- **CI (`.github/workflows/ci.yml`):** on every pull request (and by hand): `pnpm install --frozen-lockfile`, `pnpm build` (which runs `pnpm check` first, then builds the catalogue), `pnpm verify:packages`, then `pnpm release:dry` (packs the three packages with pnpm and runs `npm publish --dry-run` on each). The catalogue's `dist` is uploaded as an artifact.
- **Release (`.github/workflows/release.yml`):** on every push to `main`. It runs `pnpm check`, picks the version (`scripts/release-version.mjs`: the `package.json` version when npm does not have it and it is newer, otherwise the next patch after npm's newest), `pnpm build:packages` and `pnpm verify:packages`, publishes `@antfabric/ui-core`, `ui-react` and `ui-react-native` to npm (`scripts/publish-packages.mjs`: pnpm packs, npm publishes through trusted publishing, so there is no token; provenance once the repository is public), tags the commit `v<version>` and makes a GitHub release. `RELEASING.md` is the whole procedure.
- **Never publish by hand** and never push a release tag yourself; merging to `main` publishes. To start a minor or major, raise the version in the three `package.json` files; note consumer-visible changes in each `CHANGELOG.md`.
- **Catalogue hosting** is not set up yet; `pnpm build` writes it to `apps/catalogue/dist`.
